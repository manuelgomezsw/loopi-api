# Implementation Plan: Multi-Schema Database Configuration

**Branch**: `feature/001-multi-schema-db` | **Date**: 2026-05-03 | **Spec**: `specs/001-multi-schema-db/spec.md`

## Summary

Separate the single `loopi` MySQL schema into `loopi_dev` (for development and test) and `loopi_prod` (for production) within the existing Cloud SQL instance. A new `APP_ENV` environment variable (`development` | `test` | `production`) drives schema selection automatically — the application fails at startup with a descriptive error if `APP_ENV` is missing or has an unrecognized value.

### Phase 1: Config — APP_ENV Validation and Schema Mapping (Core Change)

1. In `pkg/config/config.go`:
   - Add `getEnvRequired(key string) (string, error)` — returns `fmt.Errorf("required environment variable %q is not set", key)` if unset or empty
   - Add `resolveDBName(appEnv string) (string, error)` — maps:
     - `"development"` → `"loopi_dev"`
     - `"test"` → `"loopi_dev"`
     - `"production"` → `"loopi_prod"`
     - anything else → `fmt.Errorf("unknown APP_ENV value %q: must be development, test, or production", appEnv)`
   - In `Load()`: read `APP_ENV` via `getEnvRequired("APP_ENV")`, then call `resolveDBName(appEnv)` to set `DatabaseConfig.Name`
   - Remove `DB_NAME` env var from config loading — schema name is now derived, not configured directly

2. In `pkg/config/config_test.go` (new file):
   - Test `resolveDBName("development")` → `"loopi_dev"`
   - Test `resolveDBName("test")` → `"loopi_dev"`
   - Test `resolveDBName("production")` → `"loopi_prod"`
   - Test `resolveDBName("staging")` → error with value in message
   - Test `Load()` returns error when `APP_ENV` is unset, error names the variable
   - Test `Load()` succeeds with `APP_ENV=development`
   - Test `Load()` succeeds with `APP_ENV=production`

### Phase 2: Infrastructure Setup Script

1. Create `migrations/013_create_schemas.sql`:
   - `CREATE SCHEMA IF NOT EXISTS loopi_dev` with `utf8mb4` charset
   - `CREATE SCHEMA IF NOT EXISTS loopi_prod` with `utf8mb4` charset
   - Comment block with full operator runbook:
     1. Dump `loopi` data: `mysqldump -u <user> -p loopi > loopi_backup.sql`
     2. Restore into `loopi_dev`: `mysql -u <user> -p loopi_dev < loopi_backup.sql`
     3. Restore into `loopi_prod`: `mysql -u <user> -p loopi_prod < loopi_backup.sql`
     4. Update `app.yaml` → `APP_ENV=production` and deploy
     5. Verify connectivity and data integrity in both schemas
     6. Drop `loopi` only after verification: `DROP SCHEMA loopi;`
   - **Rollback procedure** (if step 3–4 fail): `DROP SCHEMA loopi_prod; DROP SCHEMA loopi_dev;` — original `loopi` schema is untouched and remains the active one

2. Add a `## Database Setup` section to `README.md` explaining:
   - The two-schema model and `APP_ENV` values
   - How to run the setup script on Cloud SQL
   - The rollback procedure
